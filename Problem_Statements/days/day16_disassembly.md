# Day 16 Disassembly Supplement: What the Test Program *Actually* Does

This is a sibling reference to [day16_function_guide.md](day16_function_guide.md).
The function guide explains the Haskell — the ALU, `deduceCodes`,
the run loop. This supplement answers the question the function
guide leaves dangling:

> Part 2 reverse-engineered the opcode mapping, then ran a
> 800-ish-instruction program to "compute" the answer in register 0.
> But *what is the program computing*? Is it a real algorithm
> hidden inside ALU-test material, the way [Day 19](day19_function_guide.md)
> hides σ(N) inside a brute-force divisor scan?

**Short answer**: no. Day 16's test program is *deliberately
content-free*. It is 868 instructions of straight-line arithmetic
that compute one constant — your Part 2 answer — using every one
of the 16 opcodes in non-trivial ways. Its purpose is not to
compute anything *interesting*; its purpose is to **verify that
you classified every single opcode correctly**, because misreading
any one of them by a single rank would make the simulation diverge.
This is the meta-pattern *before* the meta-pattern — Day 19 hides a
real algorithm in a slow loop; Day 16 hides nothing at all in a
long straight line.

> **Disclaimer on input-specificity.** The opcode mapping and the
> test program below are *your input*. Every AoC solver gets a
> different permutation of opcode numbers and a different test
> program assembled to a different target constant. The structural
> observations (no flow control, every opcode used, code-generator
> snippet shape, monotone register climb) hold for every input;
> the literal numbers do not.

## The opcode mapping (this input)

After `deduceCodes` runs over all 784 samples in this input, the
sixteen numeric opcodes map as:

| Code | Op     | Code | Op     | Code | Op     | Code | Op     |
|-----:|--------|-----:|--------|-----:|--------|-----:|--------|
|  0   | `bori` |  4   | `setr` |  8   | `gtri` |  12  | `banr` |
|  1   | `borr` |  5   | `addr` |  9   | `bani` |  13  | `eqri` |
|  2   | `seti` |  6   | `gtir` |  10  | `muli` |  14  | `addi` |
|  3   | `mulr` |  7   | `eqir` |  11  | `gtrr` |  15  | `eqrr` |

This is exactly the output of [scripts/day16_disassemble.hs](../../scripts/day16_disassemble.hs).
It is *your* permutation; other solvers got different ones.

A quick sanity check on the shape: every category is represented —
two adds (`addr`, `addi`), two muls (`mulr`, `muli`), four bitwise
(`banr`/`bani`/`borr`/`bori`), two sets (`setr`, `seti`), three
greater-than (`gtir`/`gtri`/`gtrr`), three equals
(`eqir`/`eqri`/`eqrr`). The complete instruction set is 16, and all
16 codes are assigned.

## How the mapping was deduced: constraint intersection + singleton elimination

The function guide explains the *machinery* of [`deduceCodes`](day16_function_guide.md#deducecodes----constraint-propagation)
in the abstract — intersect, then eliminate. This section shows
both halves working on the actual samples for this input. (Same
data as above, generated by the same script.)

### Step 1: per-code candidate set after intersection

For every opcode number 0..15, run `matchingOps` over every sample
that uses that code, intersect the resulting sets, and you get the
*candidate set after intersection*. Any singleton at this stage is
forced by intersection alone — no elimination needed. Anything
larger needs the second pass.

| Code | Samples | Candidate set after intersection                                                            | Size |
|-----:|--------:|---------------------------------------------------------------------------------------------|-----:|
|    0 |      58 | `{addi, mulr, banr, borr, bori, setr, seti, gtri, eqir, eqrr}`                              |   10 |
|    1 |      49 | `{mulr, banr, bani, borr, setr, seti, eqir, eqrr}`                                          |    8 |
|    2 |      40 | `{banr, bani, seti, gtir, gtri, gtrr, eqir, eqri, eqrr}`                                    |    9 |
|    3 |      48 | `{mulr, banr, bani, seti, gtir, gtri, eqri, eqrr}`                                          |    8 |
|    4 |      58 | `{setr, gtir}`                                                                              |    2 |
|    5 |      55 | `{addr, addi, seti}`                                                                        |    3 |
|    6 |      50 | `{gtir, gtri, gtrr, eqir, eqri, eqrr}`                                                      |    6 |
|    7 |      55 | `{gtri, gtrr, eqir}`                                                                        |    3 |
|    8 |      40 | `{gtri, gtrr}`                                                                              |    2 |
|    9 |      43 | `{bani, gtir, gtri, gtrr, eqir, eqri, eqrr}`                                                |    7 |
|   10 |      55 | `{addr, addi, mulr, muli, banr, bani, borr, bori, setr, seti, gtir, gtri, gtrr}`            |   13 |
| **11** | **46** | **`{gtrr}`** — the only code forced by intersection alone                                   | **1** |
|   12 |      41 | `{banr, bani, gtir, gtri, gtrr, eqir, eqri, eqrr}`                                          |    8 |
|   13 |      53 | `{gtri, gtrr, eqir, eqri}`                                                                  |    4 |
|   14 |      41 | `{addi, mulr, seti}`                                                                        |    3 |
|   15 |      52 | `{eqir, eqrr}`                                                                              |    2 |

Observations:
- **Sample distribution is roughly uniform** — 40 to 58 samples per
  code. That gave intersection enough independent constraints to
  prune most candidate sets down to 2–4 ops; without that volume,
  intersection alone leaves too many ambiguities.
- **Only code 11 is a singleton at this stage.** Even after 46
  independent samples have all said "the operation behind code 11
  is one of these", the *only* op consistent with every one of
  them is `gtrr`. This is the anchor the entire elimination cascade
  hangs from.
- **Code 10's candidate set has 13 entries.** Its samples are the
  least informative — most ops would explain them. It is the last
  code resolved; by the time round 16 reaches it, 15 ops have been
  removed and the remaining one (`muli`) is what's left.
- **`muli` appears in *exactly one* candidate set** at this stage —
  code 10's 13-element set. Every other code's samples actively
  *exclude* `muli`, so `muli` can only land at code 10. That's
  what makes code 10 the last to resolve: no other code is
  "competing" for `muli`, so it stays put through every other
  round until it is the only op left.

### Step 2: singleton elimination trace

With the table above as input, repeatedly pick a code whose
candidate set is a singleton `{op}`, fix `code -> op`, and delete
`op` from every other code's candidate set. The 16 rounds for
this input:

| Round | Code | → Op   | Why singleton                                                              |
|------:|-----:|--------|----------------------------------------------------------------------------|
|     1 |   11 | `gtrr` | Already `{gtrr}` by intersection (the anchor)                              |
|     2 |    8 | `gtri` | Was `{gtri, gtrr}`; round 1 removed `gtrr`                                 |
|     3 |    7 | `eqir` | Was `{gtri, gtrr, eqir}`; rounds 1–2 removed `gtrr` and `gtri`             |
|     4 |   13 | `eqri` | Was `{gtri, gtrr, eqir, eqri}`; rounds 1–3 removed `gtrr`, `gtri`, `eqir`  |
|     5 |   15 | `eqrr` | Was `{eqir, eqrr}`; round 3 removed `eqir`                                 |
|     6 |    6 | `gtir` | Was `{gtir, gtri, gtrr, eqir, eqri, eqrr}`; rounds 1–5 removed the other 5 |
|     7 |    4 | `setr` | Was `{setr, gtir}`; round 6 removed `gtir`                                 |
|     8 |    9 | `bani` | Was `{bani, gtir, gtri, gtrr, eqir, eqri, eqrr}`; rounds 1–7 removed 6     |
|     9 |   12 | `banr` | Was `{banr, bani, gtir, gtri, gtrr, eqir, eqri, eqrr}`; 7 removed by now   |
|    10 |    2 | `seti` | Was `{banr, bani, seti, gtir, gtri, gtrr, eqir, eqri, eqrr}`; 8 gone       |
|    11 |    3 | `mulr` | Was `{mulr, banr, bani, seti, gtir, gtri, eqri, eqrr}`; 7 gone             |
|    12 |    1 | `borr` | Was `{mulr, banr, bani, borr, setr, seti, eqir, eqrr}`; 7 gone             |
|    13 |   14 | `addi` | Was `{addi, mulr, seti}`; rounds 10–11 removed `seti` and `mulr`           |
|    14 |    0 | `bori` | Was 10-element set; rounds 1–13 left only `bori`                           |
|    15 |    5 | `addr` | Was `{addr, addi, seti}`; rounds 10, 13 removed `seti` and `addi`          |
|    16 |   10 | `muli` | Was 13-element set; only `muli` survives after 15 rounds                   |

Reading this as a *deduction cascade*: code 11 falls first as the
intersection-only singleton. That removes `gtrr` from codes 8, 7,
13, 6, 9, 12, 2 — each of which loses one option. Code 8 (`{gtri,
gtrr}`) was *almost* a singleton already; with `gtrr` gone it
collapses immediately. That removes `gtri`, which collapses
code 7 (`{gtri, gtrr, eqir}` → `{eqir}`). Each newly-resolved op
unlocks one or two more codes. The cascade visits all 16 codes in
exactly 16 rounds with no backtracking — proof that this input is
*uniquely determined* (which AoC promises but the algorithm has to
discover).

This is the "naked single" rule from Sudoku, applied to a
bipartite matching: 16 numeric codes on one side, 16 ops on the
other, every sample is an edge constraint, and the greedy
"resolve-and-strike" loop finds the unique perfect matching when
one exists. The same shape resolves any *exact-cover* puzzle when
the input is well-conditioned — Day 7 (topological sort) was a
cousin, and any project-Euler "permutation with constraints"
puzzle is too.

### Why this works at all

Two stars have to align for `deduceCodes` to terminate cleanly:

1. **Every code must have a singleton in its closed orbit.** If the
   constraint intersection produces *no* initial singleton anywhere,
   the elimination loop has nothing to start with. AoC guarantees a
   singleton exists (this input has code 11); a hypothetical puzzle
   without one would require backtracking search instead.
2. **Each resolved op must not strand another code.** When we
   remove an op from all candidate sets, no code's set may go
   empty. AoC guarantees this too. (If it did happen, `solve'`
   would loop forever on a stuck state — though in practice the
   algorithm would just produce an empty mapping and fail
   downstream.)

Day 16's input was generated with these guarantees baked in. The
sample volume (784 samples, ~50 per code) provides enough
constraint to keep intersection useful; the puzzle author chose
the opcode permutation so at least one code had a clean singleton
to seed the cascade.

## The program at a glance

The test program is **868 instructions** long. Histogram of opcode
usage in the program (not the samples — the program itself):

| Op     | Count | Pct  | Op     | Count | Pct |
|--------|------:|-----:|--------|------:|----:|
| `seti` |   260 | 30%  | `eqir` |    11 | 1%  |
| `muli` |   229 | 26%  | `gtrr` |    10 | 1%  |
| `addr` |   129 | 15%  | `gtir` |     9 | 1%  |
| `setr` |    91 | 10%  | `banr` |     9 | 1%  |
| `addi` |    65 |  7%  | `eqri` |     8 | 1%  |
| `mulr` |    12 |  1%  | `eqrr` |     7 | 1%  |
| `bani` |    12 |  1%  | `gtri` |     6 | 1%  |
|        |       |      | `bori` |     6 | 1%  |
|        |       |      | `borr` |     4 | <1% |

**All sixteen opcodes appear at least four times.** This is the
single most important structural observation — the program
*requires* you to have classified every opcode correctly. Miss one
and your simulation diverges, your final r0 is wrong, and you get
a wrong answer. The puzzle generator deliberately tuned the
frequencies so the rare ones (`borr`, `gtri`, `bori`) still appear
enough to materially affect the result.

Note the heavy bias toward simple constant manipulation: `seti` +
`muli` + `addi` + `addr` + `setr` together are **775 of 868
instructions = 89%**. The exotic opcodes (bitwise, comparisons)
are the spice; the bread is "set a small constant, multiply it,
add it somewhere".

## No flow control = straight-line constant computation

This is the deepest observation about Day 16's test program. The
puzzle text says it outright:

> the device's opcodes don't contain any flow control like jump
> instructions.

That isn't an idle remark — it is what makes Day 16's program
*completely different* from Day 19's. In Day 16 the IP increments
by exactly +1 after every instruction; there is no way to loop, no
way to branch, no way for the program to depend on its input.

The four registers all start at zero. With no jumps, every register
at every step is a deterministic function of those four zeros, so
**the whole 868-instruction program reduces to a single constant**
— your Part 2 answer, 472. Step 868 always lands on `[472, 472, 6, 3]`
(give or take the housekeeping registers); steps 0..867 are a long
construction proof that 472 is what it is.

It is, *literally*, the most obfuscated way to write `print(472)`
that the puzzle author could think of inside the constraints of a
16-opcode no-jump ISA.

Day 19 fixes the no-jump problem (the IP is bound to a register, so
add/set become jumps) and the difference is immediate: a Day 19
program *can* loop, *can* depend on its initial state, and *does*
embed a real algorithm (σ(N) brute-force). Day 16 cannot, and
doesn't.

## Anatomy of a snippet

The program reads as a sequence of self-contained snippets, each
≈ 5–10 instructions long, each computing a small constant and
adding it to a running register (r0 or r1).

Here are the first three snippets, transcribed from
[scripts/day16_disassembly.txt](../../scripts/day16_disassembly.txt)
with running register state on the right:

```
ip  opcode  a b c  ; comment                    regs after
 0  seti    2 3 3  ; r3 = 2                     [0,0,0,2]
 1  seti    0 3 2  ; r2 = 0                     [0,0,0,2]
 2  seti    2 1 0  ; r0 = 2                     [2,0,0,2]
 3  eqrr    0 3 3  ; r3 = (r0 == r3) ? 1 : 0    [2,0,0,1]
 4  muli    3 1 3  ; r3 = r3 * 1                [2,0,0,1]
 5  addr    1 3 1  ; r1 = r1 + r3               [2,1,0,1]   <-- snippet 1 done, +1 to r1
 6  seti    2 3 3  ; r3 = 2                     [2,1,0,2]
 7  muli    1 0 0  ; r0 = r1 * 0                [0,1,0,2]
 8  addi    0 0 0  ; r0 = r0 + 0                [0,1,0,2]   (no-op padding!)
 9  eqir    2 3 2  ; r2 = (2 == r3) ? 1 : 0     [0,1,1,2]
10  muli    2 3 2  ; r2 = r2 * 3                [0,1,3,2]
11  addr    1 2 1  ; r1 = r1 + r2               [0,4,3,2]   <-- snippet 2 done, +3 to r1
12  setr    1 1 0  ; r0 = r1                    [4,4,3,2]
13  seti    3 2 1  ; r1 = 3                     [4,3,3,2]
14  muli    1 0 2  ; r2 = r1 * 0                [4,3,0,2]
15  addi    2 0 2  ; r2 = r2 + 0                [4,3,0,2]   (no-op padding!)
16  banr    1 3 3  ; r3 = r1 & r3 = 3 & 2 = 2   [4,3,0,2]
17  muli    3 3 3  ; r3 = r3 * 3                [4,3,0,6]
18  addr    3 0 0  ; r0 = r3 + r0               [10,3,0,6]  <-- snippet 3 done, +6 to r0
```

Three snippets, three contributions: +1 to r1, +3 to r1, +6 to r0.
After 18 instructions, r0 = 10 and r1 = 4. By instruction 868,
r0 = 472.

Two structural features to notice:

- **No-op padding.** Look at instructions 7-8 and 14-15.
  `r0 = r1*0` (a *zeroer* — r0 becomes 0 regardless of r1) followed
  by `r0 = r0+0` (a pure no-op). Likewise `r2 = r1*0; r2 = r2+0`.
  These do nothing to the running total but they *do* exercise the
  `muli`/`addi`/`mulr` dispatch — and that's the point. Many of
  the program's 868 instructions are filler whose only function is
  to make sure the rarer opcodes get tested.

- **Always-true comparisons.** Instruction 3 is `eqrr 0 3 3`,
  which sets r3 to 1 if r0 == r3. r0 and r3 are both 2 at that
  point (set deterministically by instructions 0 and 2), so the
  result is *always* 1. Instruction 9 is the same trick for
  `eqir`. The puzzle generator chose operands so the comparisons
  return a known constant — which is then multiplied by another
  known constant and added to the running total. From the
  *outside*, you have to actually decode `eqrr`, `eqir`, etc.
  correctly. From the *inside*, it is `1` and the result is
  predetermined.

The whole program is this repeated all the way down:

> set up some registers to known constants → run a comparison or
> bitwise op whose result is therefore *also* a known constant →
> multiply that result by another constant → add it to the running
> total

Each snippet contributes a small positive number to r0 or r1, and
the running total climbs monotonically toward 472.

The "big" value (the running total) gets passed around between
registers as the snippets transfer it — sometimes it lives in r1,
sometimes in r3, sometimes in r0 — but the *maximum* register is
monotone non-decreasing across each ~50-step window: 27, 68, 93,
131, 159, 183, 202, 223, 248, 280, 292, 326, 345, 374, 413, 447,
466, 472.

The increments per 50 instructions average ~26 (range 9–44),
consistent with ~5 snippets per 50 instructions each contributing a
small constant. Over 868 instructions ≈ 87 snippets, average
contribution ≈ 5.4. That is roughly the structure the puzzle
generator produced.

## Why it is built this way: the meta-problem

The Part 2 *puzzle text* asks you to:

1. Cross-reference 784 samples to deduce the 16-opcode mapping.
2. Run the test program from zero, report register 0.

What the puzzle author *actually* tested:

1. **Did you classify every opcode correctly?** All 16 appear in
   the test program; misreading any single one changes the
   simulation's output. There is no way to fake your way to 472
   without all 16 mappings right.

2. **Did you implement the ALU correctly?** The 89% of `seti` /
   `muli` / `addi` / `addr` / `setr` are easy to get right; the
   11% of bitwise + comparisons (`bani`, `borr`, `gtir`, etc.) are
   where most bugs would land. The program forces those rare
   opcodes through real-data paths.

The 868-instruction program is, structurally, a **checksum** —
specifically a 4-register polynomial digest over the 16-opcode
table you produced. If your table is right, the digest is 472; if
your table is off by *one* swap (say you read `bani` as `banr`),
the digest is some other number, you get a wrong answer, and you
go back and debug.

This is *anti-content*: the program does not represent a
computation in any algorithmic sense, the way a Fibonacci or
divisor-sum program would. It is content-free by design — every
solver gets a different 868-instruction program assembled by the
puzzle generator to produce a different ~3-digit target constant.
The constant itself is the *only* thing computed; everything else
is scaffolding to make sure all 16 opcodes participate in
producing it.

(This is also why Part 2 runs in 802 µs in our benchmark —
868 instructions × 4-register `(//)` updates × the natural cost of
a `case` dispatch. There is nothing algorithmically slow because
there is no algorithm.)

## Where this lands in the 16 / 19 / 21 trilogy

The three "build a VM" puzzles of AoC 2018 are calibrated to escalate:

| Day | Test program is...                                            | Reverse-engineering task    |
|----:|---------------------------------------------------------------|-----------------------------|
| 16  | Anti-content: 868 instructions producing one constant.        | Identify all 16 opcodes.    |
| 19  | A real algorithm hidden in brute force: σ(N).                 | Read assembly; compute σ(N).|
| 21  | (forward reference) Another real algorithm — TBD when solved. | TBD                         |

Day 16 is the *opcode-identification* puzzle. Day 19 is the
*program-comprehension* puzzle (the assembly is meaningful). Day 21
will be the *interactive program-comprehension* puzzle (Part 1 will
be passive observation; Part 2 will be something close to "what is
the longest non-repeating input").

Reading Day 16's program as if it were Day 19's would lead you to
spend hours looking for an algorithm that is not there. The
function guide on its own does not surface this; that's what this
supplement is for. Once you know the shape — *anti-content,
checksum-style, all-16-opcodes-validated* — Day 16 reads as a
contained Phase 1 of a three-phase reverse-engineering arc, and
Day 19's Part 2 lands as the *real* version of the move Day 16 was
preparing you for.

## Reproducing this analysis

The disassembly was produced by
[scripts/day16_disassemble.hs](../../scripts/day16_disassemble.hs),
which imports Day 16's exposed `parseInput` / `deduceCodes` /
`applyOp` and prints (a) the opcode mapping, (b) the disassembled
program with per-instruction commentary, and (c) a step-by-step
register trace.

Run from the repo root:

```
runghc -isrc scripts/day16_disassemble.hs > scripts/day16_disassembly.txt
```

The 1,758-line output is checked in at
[scripts/day16_disassembly.txt](../../scripts/day16_disassembly.txt)
as a frozen reference for this supplement. Re-running it on a
different `inputs/day16.txt` produces a different mapping and a
different program with a different target constant, but the same
*shape* of analysis applies.
